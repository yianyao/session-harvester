# Agent 会话轨迹分析工具 —— 设计方案 v1.0

> 日期：2026-10-05
> 约束：1–2 人小团队；单一公司内部场景，≤20 名使用者
> 上游文档：《轨迹分析工具可行性评审报告.md》（含二次评审附录）
> 决策基线：厚语料、薄分析；2.2+2.3 为核心，2.4 并入 2.2 查询视图，2.1 以知识卡片形态后置

---

## 1. 目标与非目标

### 1.1 目标

| 编号 | 目标 | 产物 |
|---|---|---|
| G1 (2.2) | 工具/技能使用诊断 | 工具失败率/重试率/放弃率报告；改进建议 |
| G2 (2.3) | Harness 踩坑发现 | 错误三分类分布；对接 ~/.dsh/AGENTS.md 的条目建议 |
| G3 (2.1) | 知识卡片（为日后知识库作准备） | 带 YAML frontmatter 的 Markdown 卡片库，锚点可溯 |
| G4 (2.4→G1) | 行为画像（服务于技能改进） | "围绕技能使用的行为序列"查询视图（群体层面） |

### 1.2 非目标（明确不做）

- 实时流式分析（T+1 批处理足够）
- Web 前端/仪表盘（CLI + Markdown 报告）
- 分布式/任务队列/向量数据库/图数据库
- 个人级画像输出；任何能力/态度类敏感推断
- 效果验证闭环（"条目有效性前后对比"以月计，第一版只做发现+建议）

## 2. 总体架构

```
┌────────────────────────────────────────────────────┐
│ 采集层（双源双轨）                                    │
│  WorkBuddy adapter ← transcript JSONL (259.6MB 实测) │
│  DSH adapter       ← 原始会话 JSONL（zstd 可选依赖）    │
│  dsh-chat-import   ← 仅作交叉验证器与快速扩源桥        │
└──────────────────────┬─────────────────────────────┘
                       ↓  统一内部 schema（标准 SQL，可移植）
┌────────────────────────────────────────────────────┐
│ 存储层：SQLite（WAL）+ FTS5 bigram 预分词             │
│  锚点 = (session_id, turn, message_id, step_id)     │
│  预计全库 1–2 GB，建库分钟级                          │
└──────────────────────┬─────────────────────────────┘
                       ↓
┌────────────────────────────────────────────────────┐
│ 诊断层（确定性，无 LLM）                              │
│  report-tools / report-errors / query / regress     │
└──────────────────────┬─────────────────────────────┘
                       ↓
┌────────────────────────────────────────────────────┐
│ 提炼层（LLM，可抛弃设计，单组件 ≤2 人天）              │
│  错误归因 / 知识卡片生成（markdown+frontmatter）      │
│  交叉验证：置信度 + 每批 10 条人工抽样复核             │
└────────────────────────────────────────────────────┘
```

投资纪律：存储层与锚点体系按**永久资产**投入；提炼层按**可抛弃**设计——模型进步替代它视为收益而非损失。

## 3. 统一内部 schema（v1）

```sql
-- 源登记
sources(source_id PK, name, adapter_version, schema_fingerprint, ingested_at)

-- 会话
sessions(session_id PK, source_id FK, external_id,
         user_hash,            -- 只存哈希（隐私硬约束）
         started_at, ended_at, turn_count, meta JSON)

-- 步骤（轨迹的最小单元）
steps(step_id PK, session_id FK, turn, message_id, seq,
      role,                -- user | assistant | system
      kind,                -- user_input | model_decision | tool_call |
                           -- tool_result | system_inject | error
      ts, content)

-- 工具调用与结果
tool_calls(call_id PK, step_id FK, session_id FK,
           tool_name, args_summary, started_at, dur_ms)
tool_results(result_id PK, call_id FK, step_id FK,
             is_error INTEGER,
             error_class,      -- env | tool_interface | context | NULL
             content_summary)

-- 知识卡片索引（卡片本体是 markdown 文件，SQLite 只做检索）
cards(card_id PK, path UNIQUE, title, card_type, tags JSON,
      anchors JSON,          -- [{session_id, turn, message_id}]
      confidence REAL, created_at)

-- FTS
steps_fts: FTS5(bigram 预分词), content 列同步自 steps.content
```

锚点不单设表，由 `session_id + turn + message_id + step_id` 承载；所有下游产物（报告行、卡片、归因结论）必须携带锚点。

可移植性纪律：除 FTS5 外不使用 SQLite 专属特性，schema 保持标准 SQL，保留向 DuckDB/PostgreSQL 迁移的退路。

## 4. 采集层设计

### 4.1 WorkBuddy adapter（主路径之一）

- 输入：`~/.workbuddy/projects/*/*.jsonl`（transcript），已确认 259.6 MB 真实语料可用。
- 保留 memory-log 通道但降级为独立 category，标注"非对话轨迹"，不污染轨迹语料。
- 关键字段映射：系统提示注入 → `kind=system_inject`（G2 的关键信号，不可丢）；工具 I/O → `tool_calls/tool_results`。
- 增量采集：按文件字节偏移游标（仿 OpenViking 做法），游标持久化在 `sources.meta`。

### 4.2 DSH adapter（主路径之二，隔离 0.3 风险）

- **只依赖 DSH 会话 JSONL 的字段结构，不依赖 dsh-tools npm 包**——版本天花板 `dsh-tools <0.3.0` 只约束 dsh-chat-import，不约束本路径。
- `zstandard` 作为可选依赖（extras：`pip install .[dsh]`），缺依赖时跳过压缩日志并告警，不崩。
- **schema 指纹**：ingest 时提取字段结构指纹存入 `sources.schema_fingerprint`。DSH 0.3 落地后跑指纹 diff；字段漂移 → 只改本 adapter 的 parser（预估 1–2 人天），非系统性破坏。
- OTel span（traces/）作为旁路数据源接入确定性统计（调用次数/耗时/失败率），无需 LLM。

### 4.3 dsh-chat-import（桥，降级为辅助）

- 用途一：WorkBuddy 导入结果的**交叉验证器**（M0 用一个会话实测其 toolResults/isError/系统提示保留，与自研 adapter 对账）。
- 用途二：未来快速扩展新源（Claude/Codex/Kimi 等）的格式桥。
- 明确不作为地基：附件泄漏、静默合成空结果、版本天花板三大硬伤已核验在案。

## 5. 中文检索：FTS5 + bigram 预分词

沿用已实测结论（2–5 字词 100% 命中，索引体积约 1.4–1.9x）：

- 插入侧：CJK 连续串改写为重叠二元组；查询侧 `_fts_query` 同步改写（不同步改写 = 0 命中，已实测确认）。
- 另存原文列供展示；`bm25()`/`snippet()` 正常可用。
- 已排除方案：trigram（2 字词 0 命中）、detail=none（破坏短语查询）。
- 代码量预估 40–60 行，纯标准库。

## 6. 诊断层（CLI 命令设计）

```
ingest --source workbuddy|dsh <path>   # 增量采集 + schema 指纹
report-tools --since 30d               # 每工具：失败率/重试率/平均重试次数/放弃率
                                       # 绕行检测：连续相同工具调用计数
                                       # Top3 失败工具及失败模式分布
report-errors --since 30d              # 错误三分类分布（env/tool_interface/context，
                                       # 正则映射）；按轨迹位置（开场/中途/收尾）分桶
query --fts "关键词"                    # bigram 全文检索，返回锚点+原文片段
behavior --skill <name>                # G4 视图：围绕该技能调用的用户行为序列
                                       # （重试/换工具/放弃/纠正 motif 频率，群体层面）
cards extract --session ...            # 调用提炼层生成卡片（M3）
cards validate                         # 锚点有效性 + 证据原文一致性校验
regress                                # 固定回归语料全流程跑批，输出 diff
```

放弃率定义（写入代码注释与文档）：同一工具连续失败 ≥N 次（默认 3）后转向其他工具或结束会话，记一次放弃。

## 7. 提炼层（LLM，可抛弃设计）

1. **错误归因**：输入 = 失败模式 + 锚点上下文（从 SQLite 提取）；输出 = 三分类归因 + 根因方向 + 强制原文引用；必须带置信度字段。
2. **知识卡片生成**：输入 = 思路转折点候选片段；输出 = markdown 卡片（见 §8）；每卡强制引用证据原文。
3. **交叉验证规则**：LLM 断言与确定性统计冲突时（如"该工具经常失败" vs 统计失败率 2%）以统计为准并告警；每批输出随机抽 10 条人工复核，一致率 < 80% 收紧 prompt 或缩小归因范围。
4. 每个 LLM 组件限时 2 人天；prompt 与工作流视为耗材，随模型升级重写。

## 8. 知识卡片规范（为知识库作准备）

- 形态：**带 YAML frontmatter 的 Markdown 文件**，目录即卡片库；SQLite `cards` 表仅索引。
- frontmatter 字段（现在冻结）：

```yaml
---
id: kc-20261005-0001
title: <一句话主题>
type: insight | pitfall | workflow          # 思路 / 踩坑 / 流程
tags: [...]
anchors: [{session_id, turn, message_id}]   # 强制
evidence: |                                  # 证据原文，强制
  <原文片段>
confidence: 0.0-1.0
created: 2026-10-05
---
<卡片正文>
```

- 选取标准：markdown + frontmatter 是最可移植形态，Obsidian/任意知识库可直接收编；工具本身终止时卡片资产仍存活。
- 质量规则：卡片必须带足量证据原文与锚点链接；脱离上下文的卡片视为缺陷。

## 9. 里程碑与止损

| 阶段 | 内容 | 预算 | 验收标准 |
|---|---|---|---|
| M0（1–2 天） | dsh-chat-import 单会话实测（对账自研映射）；DSH 原始日志格式勘察；schema v1 冻结 | 1–2 人天 | 双源字段映射表签字；指纹机制就绪 |
| M1（4–6 天） | 双 adapter + 全量建库（259.6MB）+ report-tools | 4–6 人天 | 能回答"过去 30 天失败率 Top3 工具及失败模式分布"；建库检查点三项数字留档（时长/体积/Top 查询延迟） |
| M2（3–5 天） | 错误三分类 + AGENTS.md 条目建议 + 回归语料（按工具覆盖率分层抽样） | 3–5 人天 | 每条建议附锚点与原文；regress 可复跑 |
| M3（5–8 天） | 知识卡片库 + LLM 提炼 + 交叉验证 | 5–8 人天 | 抽样复核一致率 ≥80%；卡片可被 Obsidian 打开 |

**止损线：M1 报告产出后一个月内未触发任何实际修改（无 AGENTS.md 条目变动、无技能修复），项目停止，沉没成本 ≤ 一周。**

## 10. 隐私硬约束（不可妥协）

1. `user_id` 只存哈希；库名、日志、报告输出中不得出现明文身份。
2. 画像（G4）仅群体层面；个人级行为查询仅限本人数据。
3. 纳入 20 人语料前完成知情同意（数据范围、用途、保留期限）。
4. 画像维度限于操作模式（重试/纠正/追问），禁止能力评价与态度倾向推断。
