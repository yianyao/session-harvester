## 2. 可优化点（按"先正确性、后成本"排序）

### 2.1 增量索引缺位（第一位：既是成本，也是**正确性**）

- **现状**：`indexing.index_sources()` 每次跑都 `DELETE FROM sessions/messages/steps`
  **全表清空重建**；`index_exports()` 同样。`indexing.py:9` 的注释自己写着
  "会话规模大到重建变慢时再考虑 mtime 增量"。
- **后果 A（成本）**：每次 `update` = 全量重读 **1964 个会话**；仅 DSH 一侧就要
  解压 42 MB（**9.1 s**，且解压占 82%）。语料只增不减 → 成本单调上涨。
- **后果 B（正确性，更严重）**：因为没有便宜的重跑手段，`update` 就跑得少——
  **实测库停在 10-09，缺 10 个会话 / ≈14 MB（含本会话 3.5 MB，mtime 17:59）**，
  且落下的 10 个**全是较新的大会话**。也就是说：**主题归位、分诊池、卡片这些分析
  结果都是在 10-09 的数据上算的**，而语料里最新最大的轨迹完全没进分析。
- **已具备的条件**：`index_session(con, rec, file=...)` 已实现"按 sid 删+插"的
  增量原语（`indexing.py:186`），只是全量入口没用它。
- **做法**：以 `(file, st_mtime_ns, st_size)` 为水位表（可放 `sessions` 加列或独立表）：
  未变 → 跳过解析（连解压都不做）；变了/新增 → 走 `index_session`；
  盘上消失 → 删该 sid 三表行；FTS 行随 sid 一并维护。
- **验收（都能说清何时会红）**：连跑两次 `update`，第二次**未变会话重解析数 = 0**；
  `sessions where source='dsh'` 计数 = **33**（与语料文件数一致）；删掉一个文件再跑
  → 该 sid 三表行消失且 `messages` 不残留。

### 2.2 库新鲜度应可检查（紧接 2.1）

`dbmeta` 已有 `db_mtime`、`db_fingerprint`，但**没有**"语料比库新多少"的显式判定，
所以"库旧了"只能靠人偶然发现（本轮就是偶然撞见）。建议：`update` 输出
`新增 / 更新 / 未变 / 删除` 四计数（`sync` 已有 `unchanged` 一项），并在报告里显示
**库龄**；`dbmeta` 增加"最新语料 mtime > 库 mtime ⇒ 标 STALE"。

### 2.3 错误判据改用结构化字段（**鲁棒性**，不是准确性）

- 现状 `dsh.py:550` 用**文本前缀** `startswith("error")`；而每条 tool/result
  **都带** `data.message.isError`（8404/8404），另有 `data.error`（179）。
- 实测今天**够用**（201/202 一致、0 漏判）。但文本判据是**脆的**：上游换措辞/本地化、
  或失败文本以 `Traceback (most recent call last)` 之类开头（**今天恰好 0 条**）就会漏。
- 做法：`is_err = bool(msg.get("isError"))`，文本判据降为**兜底**（兼容旧 frame 与其他源）；
  顺便把 `data.error`（179）里的 code/message 填进 step 的 `error` 列（比现在的 400 字预览更结构化）。
- **验收**：合成两条 tool/result——一条文本以 `Traceback` 开头但 `isError=true`
  （现口径漏、新口径抓到），一条 `isError=false` 但正文含 `Error:`（现口径误、新口径不误）。

### 2.4 无真实数据覆盖的分支（记录，不修）

真机 subagent 会话 **0 个** → `is_subagent` 判定、`[subagent]` 标题前缀、以及 C3 的
DSH schema 守卫在 subagent 形态上的行为，**只有合成夹具验证**，无真实样本。
不是缺陷，但按 H9/§五 15 如实记"未覆盖"，别让下一个会话以为它跑过真实数据。

### 2.5 已评估但不建议做

- **丢弃行仍全额 `json.loads`**：48% 行被丢，但解析只占 9.1 s 里的 1.6 s；
  加便宜前置过滤（`'"step/' in ln`）最多省 ~0.5 s，不值当（2.1 做完后更不重要）。
- **解压结果缓存**：2.1 之后不再需要；若未来要"全量首建"（新机器），可考虑
  `(path, mtime_ns, size)` → 文本缓存，或按 zstd frame 并行（实测单文件最多 247 frame）。

## 3. 自进化：能做一半，缺的那一半是"评估"

**已经机械具备（现在就在跑）**

1. **采集自己**：`source=dsh` 已在库（23 条，本轮之前）；我的三条长会话（3.5 MB 级）
   就是本工具要处理的"自己"。
2. **提炼**：`steps` **36,647** 行 → `report-errors` / `errstats` 三分类（env /
   tool_interface / context）；`tool/call` 8404 条给了行为链。
3. **产出**：`suggest-agents` → AGENTS.md 候选池 + `suggestions_meta.db` 台账
   （真库 8 条：7 adopted / 1 rejected，且 `--coverage` 能查出"6 已裁决 / 2 待裁决 /
   2 陈旧"）；`cards` / `artifacts` 是领域侧产物。
4. **度量**：`regress`（7 步 / 57 断言）+ 套件 685 例 + 各门禁。
   本会话即为实例：**我自己的工具抓到了我自己的三处缺陷**（C3 新测试的模块级打桩泄漏、
   死代码门在并发编辑下的假红、以及我第一版探针的口径错误）。

**缺的关键一环：闭环的"评估"**

现在只有两个信号——"错误计数"（输入侧）与"规则是否被采纳"（记录侧），
**没有"采纳之后有没有变好"**。所以严格说现在是**人在环路里的半自动**（机器统计、
人下判断），不是自进化。

**要补的最小设计（三步，都能判定）**

| # | 做什么 | 验收（何时算通过 / 何时该回滚） |
|---|---|---|
| 1 | `suggestions_meta` 加 **`adopted_at`**（规则并入 AGENTS.md 的时间点）——这是 A/B 的分界 | 台账里每条 adopted 都有时间戳；没有就不算"已并" |
| 2 | 新命令（如 `harvest-eval --since <adopted_at>`）：对比该**错误类**在 T 前后各 N 天的 **未解决率 / 复发率** | 输出三值判定：**实测改善 / 无变化 / 变差**；必须同时给样本量（避免小样本假显著） |
| 3 | 纪律：**无变化 = 该规则退休，变差 = 回滚** | 否则规则只增不减，AGENTS.md 膨胀成噪声墙（当前 8 条，尚小，早立规矩成本低） |

**安全边界（保持不变）**：工具**不自动改** `AGENTS.md`——只出证据与建议，人做并入
（现有铁律）。"自进化"的自，指的是**评估自动化**，不是**改动自动化**。

**信号偏差提醒**：错误计数只测"出错"，不测"做对了多少"。若真要往自进化走，
建议再加一个产出侧信号（每轮实际交付物 / 被用户纠正次数 / 返工轮次），
否则"少报错"可能是"少干活"换来的。

## 4. 建议的下一步顺序

1. **2.1 增量索引**（一次同时解决成本与"分析在旧数据上跑"）→ 2. **2.2 库龄可检查** →
2. **2.3 结构化 `isError`**（便宜、消脆性）→ 4. **§3 的 `adopted_at` + `harvest-eval`**
（这才是自进化的真闭环）；2.4/2.5 记着不做。
