## 1. 怎么在本机跑起来（README 的第一道门槛）

README 通篇写 `python -m harvester ...`，但**本机没有任何叫 `python` 的命令**：

```text
where.exe python  → NOT FOUND
where.exe py      → NOT FOUND
注册表 HKCU/HKLM\Software\Python\PythonCore → 无
%LOCALAPPDATA%\Programs\Python → 不存在
```

本机真实存在的解释器：

| 解释器 | 路径 | 备注 |
|---|---|---|
| DSH 自带运行时 | `~\.dsh\dsh-runtimes\dsh-primary-runtime\dependencies\python\python.exe` | 3.12.14，FTS5 可用，本次核查用它 |
| WorkBuddy venv | `~\.workbuddy\binaries\python\envs\default\Scripts\python.exe` | README「环境注意事项」已声明它跑不了本套件 |
| WorkBuddy 基础版本 | `~\.workbuddy\binaries\python\versions\3.13.12\python.exe` | — |

**结论**：README 里每一条命令都无法按原样复制粘贴执行。这不影响代码正确性，但
「零依赖、可移植」的卖点在实际交付上打了折。建议 README 第 0 节改成
"任选一个可用解释器并记为 `$PY`，本文所有命令的 `python` 均指它"。

下面的核查全部用 `$PY = DSH 自带 python.exe` 执行。

## 3. 四个经实测确认的缺陷

### 3.1 MCP `pack_context` 工具是坏的（同族第 4 个工具没测到）

`harvester/mcpserver.py:98`

```python
recs = [self._load_by_no(n) for n in nos]      # ← 每项是 (rec, item_dict) 二元组
return build_pack(recs, ...)                    # ← build_pack 期望 [(SessionRecord, no)]
```

`build_pack` 内部 `for rec, no in recs:` 于是把 **`item_dict`** 当成了会话序号，
`used_total += used` 把整个 outline 条目字典累加了进去。实际调用返回：

```text
tools/call pack_context {'nos': '1,5', 'tokens': 500}
  isError = False
  输出: "...\n### [{'no': 1, 'adapter': 'workbuddy', 'adapter_name': 'WorkBuddy 工作区日志', ..."
```

**退出码 0、isError=false、内容全错** —— 最坏的失败形态：静默产出垃圾而不是报错。
直接复现 `build_pack([1, 5])` 得到 `TypeError: cannot unpack non-iterable int object`，
证明类型契约被破坏。

**为什么没被测试抓住**：`tests/test_v03.py:218` 只在 `tools/list` 的
**清单**里断言了 `"pack_context"` 这个名字存在，从未 `tools/call` 调用它。
这正是"不能失败的断言等于没断言"的典型——它断言的是"这个工具被登记了"，
不是"这个工具能跑"。

修复：`recs = [(rec, n) for n in nos for rec, _it in [self._load_by_no(n)]]`，
并补一个真正调用 `tools/call pack_context` 并断言输出含会话标题的测试。

### 3.2 `weblogin check` 在当前机器上不可能成功（不是"关掉浏览器就好"）

`harvester/weblogin.py:97` 的 `_read_file_share_all()` 用
`CreateFileW(GENERIC_READ, FILE_SHARE_READ|WRITE|DELETE)` 规避 Chromium 的独占锁。
实测 8 种 access/share 组合**全部失败**：

| dwDesiredAccess | dwShareMode | 结果 |
|---|---|---|
| GENERIC_READ | 1\|2\|4（全共享） | WinError 32 |
| FILE_READ_DATA | 1\|2\|4 | WinError 32 |
| GENERIC_READ | 0 / 1 / 1\|2 / 1\|4 | WinError 32 |
| FILE_READ_ATTRIBUTES | 1\|2\|4 | ✅ 能打开（但读不到数据） |
| 0（仅打开） | 1\|2\|4 | ✅ 能打开（但读不到数据） |

对 Edge、Chrome、DeepSeek 桌面版三个产品的 `Network/Cookies` 全部如此。
`Copy-Item` 同样失败；`esentutl /y` 报 `JET_errFileAccessDenied (-1032)`。

**结论**：Chromium 打开 Cookies 库时**没有授予任何共享权限**，而 Windows 要求
*双方*都允许共享才能打开。因此"浏览器运行中读 cookie"在 Windows 上做不到——
不是参数写错，是物理上不行（除非装 VSS 快照/卷影拷贝，超出零依赖范围）。

**影响**：4 个产品全部报 LOCKED，这个命令在任何浏览器开着的机器上恒不可用。
但**代码的降级是诚实的**（明确说无法离线判定并给出两条出路），所以这是
"能力边界如实暴露"而不是撒谎。建议 README 把这条从"三级流程"改成
"**须先完全退出对应浏览器/客户端**，否则恒为 LOCKED"，否则用户会以为功能坏了。

### 3.3 `tool_result` 被整个丢弃 —— 而"工具失败率"就在这里（我核算出来的实测数据）

这是**最可惜的一个缺陷**：你想要的 2.2（工具改进）与 2.3（Harness 踩坑），
**答案已经躺在已有的 AutoClaw 库里，但 Adapter 把它扔了**。

`harvester/adapters/autoclaw.py:371-426` 只映射了 `request` / `assistant` /
`answer` / `reasoning` / `tool_call`，**没有 `tool_result` 分支**。
实测 AutoClaw 库的 `neutral_session_entries` 类型分布：

| entry_type | 条数 | Adapter 映射 |
|---|---|---|
| `tool_result` | **1697** | **未映射，全部丢弃** |
| `tool_call` | 1697 | note（仅 `--with-notes`） |
| `assistant` | 1284 | assistant |
| `reasoning` | 842 | note（仅 `--with-notes`） |
| `request` | 90 | user |
| `attachment` / `resource` | 86 / 69 | 丢弃 |
| `answer` | 32 | assistant |

后果：**你手里有 1697 次工具调用的完整结果，其中 50 次是失败，但一条都没进语料。**
`tool_result` 的 payload 结构稳定且信息完整：

```json
{"content": {...}, "details": {...}, "error": null,
 "status": "success", "toolCallId": "call_...", "toolName": "read"}
```

`status` ∈ {success, error}，`error` 是结构化对象 `{code, message, retryable}`。
我据此直接算出了**现成的"工具体检报告"**（1697 次调用，23 个工具，整体失败率 2.9%）：

| 工具 | 调用 | 失败 | 失败率 |
|---|---:|---:|---:|
| `skill_run_asset` | 3 | 3 | **100.0%** |
| `subagent_wait` | 4 | 3 | **75.0%** |
| `find` | 4 | 2 | **50.0%** |
| `browser_tool` | 24 | 10 | **41.7%** |
| `ls` | 55 | 12 | **21.8%** |
| `propose_work_plan` | 7 | 1 | 14.3% |
| `edit` | 20 | 2 | 10.0% |
| `read` | 546 | 14 | 2.6% |
| `exec` / `write` / `grep` / `web_search` … | — | 0 | 0.0% |

错误码本身就是改进线索，例如：`browser_element_obscured`、
`browser_instance_unknown`（多次）、`browser_timeout_invalid`、
`tool_permission_revoked`（`ls`/`read` 被沙箱拦 → 典型的 Harness 配置坑）、
`skill_asset_not_executable`、`skill_asset_invalid`。

**修复成本极低**：在 `autoclaw.py` 的映射分支里加一个 `tool_result` → note，
带 `toolName` / `status` / `error.code`。然后加一个 `harvest report-tools` 子命令
把上面的表格机械地算出来。**这可能是整个项目里投入产出比最高的一步**：
不需要 LLM、不需要新数据源、不需要出网，直接从已有数据里产出你的 2.2 与 2.3。

**为什么没被发现**：`autoclaw.py` 顶部的注释（第 10-37 行）详细写了 entry_type 全集，
其中明确列了 `tool_result`，但映射表里忘了它；而注释只解释了"其余类型不计入消息流，
仅统计进 extra.entry_stats"——把 `tool_result` 混在"其余类型"里一笔带过了。
测试也没有覆盖 `tool_result`（`test_v04.py` 只测了 mapping / schema 守卫 /
分支遍历 / 时间换算）。

### 3.4 FTS5 中文检索基本失效，README 严重低估了这个局限

README 第 181 行说"中文子串检索**可能**漏命中"。实测是**近乎全漏**。
用 `fts5vocab` 直接看索引里真实存在的 token：

```text
输入文档：读取浏览器 cookie 的登录态探测方案
真实 token：['读取浏览器', 'cookie', '的登录态探测方案']
```

unicode61 把**整段连续汉字（被标点/空格切开）当成一个 token**。于是：

| 检索词 | 命中 | 说明 |
|---|---|---|
| `cookie` | 1 | 英文/独立 token 正常 |
| `登录态` | 0 | **漏命中**（真 token 是 `的登录态探测方案`） |
| `浏览器` | 0 | **漏命中**（真 token 是 `读取浏览器`） |
| `登录` / `态` | 0 | 漏命中 |

对一句 12 个汉字的话做 2 字滑窗检索：**12 个窗口只有 1 个命中（8%）**。
后果：`harvester search` 和 MCP `search_history` 对中文语料**基本不可用**——
而用户的语料 100% 是中文。这直接打击了"检索层"这个最大卖点的成立性。

#### 修复方案：我最初建议 trigram，**复测后撤回，改为 bigram 预分词**

我最初建议把 tokenizer 换成 `trigram`。后续做了一轮独立复测（含对抗性核验），
**这个建议是错的**，特此更正。在真实导出语料上实测三种方案：

| 检索词 | 字数 | unicode61 | trigram | bigram |
|---|---:|---:|---:|---:|
| `浏览器` | 3 | 1 | 1 | 1 |
| `工作日志` | 4 | 8 | 8 | 8 |
| `知识库` | 3 | 1 | 3 | 3 |
| **`转换`** | **2** | 1 | **0** | 3 |
| **`方案`** | **2** | 0 | **0** | 2 |
| **`识别`** | **2** | 0 | **0** | 1 |
| `批量转` | 3 | 0 | 1 | 1 |
| `心理学文件` | 5 | 0 | 1 | 1 |
| **召回率** | | **4/8 (50%)** | **5/8 (62%)** | **8/8 (100%)** |
| 按字数（2字/3字/4字+） | | 1/3, 2/3, 1/2 | **0/3**, 3/3, 2/2 | **3/3, 3/3, 2/2** |
| 索引体积（1x/8x/40x 规模） | | 1.00x | 1.92x / 1.83x / 1.92x | 1.42x / 1.71x / **1.92x** |

**关键否定证据：trigram 对 2 字中文词是 0 命中**（FTS5 官方文档明确
"Substrings consisting of fewer than 3 unicode characters do not match any rows"）。
而**双字词是现代汉语最主要的词形**——`方案`、`识别`、`转换`、`登录`、`缓存`
这类查询恰恰是最自然的检索输入。所以 trigram 只治好了长词，把最常用的短词
彻底打死了；代价还是索引翻近一倍。

**bigram 预分词（纯标准库）是更优解**：把 CJK 连续串在**插入时**改写成重叠二元组
（Lucene CJKAnalyzer 语义），查询侧同样改写。实测 **2 字到 5 字全部 100% 命中**，
索引体积在真实规模下与 trigram 相当（都约 1.9x）。

其他实测结论（用于排除错误方案）：

- `tokenize='trigram'` 下 `bm25()` 与 `snippet()` **工作正常**（实测 bm25=-2.112、
  snippet 正常高亮）。网上流传的"trigram 导致 bm25 失效"实为 **0 行命中**被误读，
  不是 bm25 坏了。
- `detail=none` / `detail=column` 虽能把 trigram 压到 1.68x，但**直接破坏短语查询**
  （实测报错 `fts5: phrase queries are not supported`），而 substring 匹配正是靠
  短语语义——两者互斥，体积买不回来。
- **bigram 的唯一代价**：`snippet()`/`highlight()` 返回的是被改写的文本，中文片段
  会变成 `<<浏览 览器>>` 这种形态。解法很简单——在建表时**另存一列原始文本**，
  展示层用原始列自建摘要即可。英文检索不受影响（只有 CJK 串被改写）。
- **不存在"换 tokenizer 就万事大吉"**：查询侧必须同步改写，否则 0 命中。
  `indexing.py:_fts_query` 需要一并改。
- 规模上无需担心：本机真实语料合计约 0.3M 字符（AutoClaw 2.47M 字符是另一口径，
  见 4.1），三种方案建库都在 0.5s 以内、索引都在几 MB 级；40x 规模下建库最慢 0.12s。
  **短词用 LIKE 兜底在本机规模下也不会有性能问题。**

**改动量**：`indexing.py` 的 `_connect` 建表加一列原文 +
`index_session`/`index_exports`/`index_sources` 三处插入时改写 +
`_fts_query` 与 `search` 的摘要渲染。约 40-60 行，比换 tokenizer 多，但**方向是对的**。

## 4. 最严重的问题：采集的是"工作总结"，不是"会话轨迹"

这一节是本次核查的主要发现。

### 4.1 语料的实际构成

对 106 条纲要逐条 `load_session` 统计：

| adapter | 会话数 | 消息数 | 字符数 | 角色分布 | 每会话角色种类 |
|---|---|---|---|---|---|
| autoclaw | 19 | 2891 | 2,474,367 | user 41 / assistant 848 / note 2002 | 3.00（19/19 多角色） |
| vscode-copilot | 10 | 64 | 26,166 | user 18 / assistant 16 / note 30 | 0.90（3/10 多角色） |
| **workbuddy** | **77** | **77** | 169,564 | **assistant 77（只有这一个角色）** | **1.00（0/77 多角色）** |

WorkBuddy 源的 77 个"会话"，每一个都恰好是 **1 条 assistant 消息**。
源码解释了原因（`harvester/adapters/workbuddy.py:84`）：

```python
msgs = [Message(role="assistant", text=text, timestamp=date)]
```

它把 `~/.workbuddy/<工作区>/.workbuddy/memory/YYYY-MM-DD.md`
——**agent 自己写的每日工作小结**——整篇塞成一条 assistant 消息。

后果链条：

1. 这 77 条在纲要里和真实对话混排，各占一个序号；
2. 导出后，一篇"2026-07-20 工作日志.md"在导出产物里表现为
   `## [assistant]` 下的一整篇文档；
3. `read --turn` 对它们恒为 `turn 1/1`（因为只有一条消息，切不出回合）；
4. 聚合成语料后，**它们在版式上和真实对话无法区分**；
5. 于是蒸馏 skill 把"当日工作小结"当成"对话轨迹"来提炼。

**这是"用自己的答案去重建自己的思考过程"**。每日小结记的是
"我做了什么、结论是什么"，**天然不含**走过哪些弯路、哪次工具调用失败、
用户在哪一句纠偏——而后者恰恰是用户四个分析目标（2.1 思路过程、2.2 工具改进、
2.3 Harness 踩坑、2.4 用户画像）**唯一有价值的部分**。

| type | 条数 |
|---|---|
| `tool/call` | 59 |
| `tool/result` | 58 |
| `assistant/message` | 40 |

**工程障碍**：Python 3.12 **没有标准库 zstd**（`compression.zstd` 是 3.14+）。
要在"零依赖"约束下读 DSH 轨迹，只有三条路：
(a) 允许一个可选依赖 `zstandard`（已是事实标准，轮子齐全）；
(b) 调系统/Node 侧的 `zstd` 解压（引入外部进程依赖，脆弱）；
(c) 提升最低 Python 版本到 3.14（本机不现实）。
→ 建议 (a)，把它做成和 playwright 同级的"可选依赖"。

## 6. 你当前的设计思路对不对

分三句话说：

**对的（保留）**
- **"机械步骤=CLI，语义步骤=agent/skill"的分工**。这是与 RetroLens 同构的正确架构，
  也是唯一能同时做到"可复现"与"能理解"的分法。`BaseAdapter` 契约、schema 守卫、
  "实现不了就是实现不了、留接口不臆测"的铁律，工程水准高于我核验过的大多数同类项目。
- **产物是给人读的 Markdown 知识库**，而不是又一个向量库。对 2.1 和 2.3 是对的：
  你需要的是"看得见自己怎么想明白的"，不是"能相似度检索"。
- **零依赖、本地、私密**。面对"会话内容出网"的顾虑（skill-miner 要送 Anthropic），
  这条是真实优势。
- **`docs/DISTILL_PLAYBOOK.md` 与宿主解耦**。把权威定义放在宿主无关的文档里、
  skill 只做薄绑定，这个决定是对的。

**不对的（必须改）**
1. **采集目标选错了，而且是根上的错**。用"agent 自己写的每日小结"当"会话轨迹"
   来喂轨迹分析，等于用二手结论重建一手过程。你的 4 个分析目标全部依赖
   真实回合、工具调用与失败、用户纠偏——这些只在 `~/.workbuddy/projects/`（259 MB）
   和 `~/.dsh/sessions/`（21.5 MB）里，两者都没采。**在这一条修好之前，
   后面所有蒸馏投入的边际收益都很低。**
2. **`tool_result` 被整个丢弃**（3.3 节）。AutoClaw 里 1697 条工具结果、其中 50 条失败，
   一条都没进语料——而你的 2.2/2.3 全靠它。这是**成本最低的**核心修复。
3. **默认参数把最有信号的字段砍了**（4.5 节）。`--with-notes` 默认关，
   而 note 正是 2.2/2.3 的另一半证据源；playbook 的推荐命令还没带这个开关。
4. **检索层对中文基本失效**（3.4 节）。而对中文用户来说检索是刚需。
5. **数据源优先级排序错了**。README 花大量篇幅写 `weblogin`（浏览器 cookie 三级流程），
   但 3.2 节证明它在浏览器运行时**物理上不可用**；而这套流程要解决的元宝/豆包/通义
   是四个产品里优先级最低的。**真正该投入的地方（本机已有的 259 MB 真实轨迹）
   反而一行代码都没有。**

**判断错了的（需要修正认知）**
- `docs/COMPARISON.md` 第 36 行"竞品全部集中在 coding-agent JSONL 日志生态，
  本套件在细分定位上没有直接竞品"——这个结论在**2026-10-05 写的时候**大体成立，
  但**现在已经不成立**：`dsh-chat-import`（★205，明确支持 WorkBuddy 与 DSH）、
  `OpenViking ingest`（明确支持 workbuddy）、`dsh-session-flow`（DSH 专属）都已存在。
  COMPARISON.md 需要一次重写，否则你会基于过时的竞品判断继续投入采集层。
